# تقرير تطوير Tijvorya نحو منصة احترافية عالمية — الإصدار 2.0

**تاريخ المراجعة:** 31 يوليو 2026  
**نطاق العمل:** مراجعة وتحسين الكود المرفق، تجربة الواجهة العامة، الأمان، الشراء، SEO، التواصل، قابلية التشغيل والإطلاق.

## الخلاصة التنفيذية

يمتلك المشروع أساسًا تقنيًا جيدًا لمنصة تجارة اجتماعية: Next.js وReact وSupabase وCloudinary وOpenAI، مع متاجر ومنتجات وطلبات ورسائل وريلز ذكية ولوحات تشغيل. تم تحويل النسخة من نموذج قوي قابل للعرض إلى **أساس إنتاج أكثر احترافية وأمانًا**.

لا يمكن لأي تعديل برمجي وحده ضمان ملايين العملاء أو الوصول العالمي. النجاح العالمي يحتاج إلى جانب الكود: اختيار سوق أول واضح، شبكة تجار، مخزون موثوق، دفع وشحن محليين، خدمة عملاء، تسويق، امتثال قانوني، وقياس مستمر للتحويل والاحتفاظ.

## أهم التحسينات المنفذة

### 1. واجهة عامة أكثر احترافية وتحويلًا
- إعادة بناء الصفحة الرئيسية برسالة قيمة واضحة للتاجر والمتسوّق.
- إضافة أقسام للثقة، التجارة عبر الريلز، التشغيل، الذكاء الاصطناعي المسؤول، الجاهزية العالمية، والأسئلة الشائعة.
- تحسين رأس الموقع وتذييله، التنقل النشط، تبديل اللغة مع الحفاظ على الصفحة الحالية، والوصول عبر لوحة المفاتيح.
- تحسين بطاقات المنتجات والمتاجر، النصوص البديلة، أزرار المفضلة، حالات المخزون، والفلاتر.
- تطوير السوق ليبحث في المنتج والمتجر والوصف، مع تصنيف وفرز ومفضلة وتصفية المنتجات المتوفرة.

### 2. تأمين عملية الشراء
- إلغاء الاعتماد على السعر والإجمالي القادمين من المتصفح.
- إنشاء الدالة الآمنة `create_checkout_order` داخل PostgreSQL.
- قفل صفوف المنتجات أثناء الطلب لمنع تعارض المخزون.
- إعادة حساب الأسعار ورسوم التوصيل من قاعدة البيانات.
- التحقق من حالة المنتج والمتجر والمخزون وخيار المنتج.
- منع جمع منتجات من متاجر مختلفة في طلب واحد.
- خصم المخزون وإنشاء الطلب وعناصره داخل معاملة واحدة.
- منع الإدخال المباشر في جدولي الطلبات وعناصر الطلب من المتصفح.

### 3. تشديد الصلاحيات الإدارية
- إلغاء اعتبار الحساب الإداري غير المصنف مديرًا عامًا تلقائيًا.
- اعتماد سياسة **المنع افتراضيًا** عند غياب `admin_role`.
- منع الاعتماد على `user_metadata` لتحديد الصلاحيات الحساسة.
- ربط رفع الوسائط وأدوات الذكاء الاصطناعي بدور موثوق من جدول `profiles`.
- إضافة دالة `admin_update_profile` لتغيير الأدوار والحالات وفق قواعد واضحة:
  - المدير العام فقط يغير الأدوار والصلاحيات الإدارية.
  - دعم العملاء يستطيع تفعيل أو تعليق الحسابات غير الإدارية فقط.
  - لا يستطيع المدير تعديل صلاحياته الإدارية بنفسه.
- تقييد التحديث المباشر لجدول الحسابات إلى الحقول الشخصية الآمنة فقط.

### 4. SEO واكتشاف عالمي
- إضافة Metadata احترافية للعربية والإنجليزية.
- إضافة canonical وhreflang وOpen Graph وTwitter Cards.
- إضافة `robots.txt` و`manifest.webmanifest` وخريطة موقع.
- جعل خريطة الموقع تشمل صفحات المنتجات والمتاجر الفعلية من Supabase.
- إضافة Metadata ديناميكية لكل منتج ومتجر.
- إضافة بيانات منظمة JSON-LD للمؤسسة والموقع والمنتجات والمتاجر.
- إضافة إعداد تحقق Google ومتغير عنوان الموقع الرسمي.

### 5. نموذج تواصل حقيقي وآمن
- استبدال النموذج الوهمي بمسار API حقيقي يحفظ الطلبات في Supabase.
- إضافة تحقق Zod، حقل honeypot، حد لحجم الطلب، وحد مؤقت للرسائل.
- استخدام `SUPABASE_SERVICE_ROLE_KEY` على الخادم فقط.
- منع العملاء من الكتابة المباشرة إلى جدول طلبات التواصل لتجنب تجاوز مكافحة الرسائل المزعجة.

### 6. جاهزية الإنتاج وتجربة الاستخدام
- عدم عرض البيانات التجريبية للحظات عند تشغيل وضع الإنتاج.
- إضافة عملة افتراضية قابلة للضبط عبر البيئة.
- إضافة صفحة صحة للخدمات تعرض حالة الإعداد دون كشف الأسرار.
- إضافة رؤوس أمنية أقوى، HSTS في الإنتاج، ضغط الاستجابة وReact Strict Mode.
- تحسين صفحة الدفع ورسائل الأخطاء والتحقق من أطوال الحقول.
- تحسين الوصول في السلة والأزرار والتسميات والحالات الحية.
- توسيع سياسة الخصوصية وشروط الاستخدام بالعربية والإنجليزية مع تنبيه واضح لضرورة المراجعة القانونية لكل سوق.

## خطوات تشغيل النسخة الإنتاجية

### مشروع Supabase جديد
نفّذ محتوى `supabase/schema.sql` مرة واحدة من SQL Editor.

### مشروع Supabase قائم على الإصدار 1.8
نفّذ فقط:

```text
supabase/migrations/20260731_v2_0_global_foundation.sql
```

### إنشاء أول مدير عام
لا تسمح الواجهة بترقية مستخدم إلى مدير حفاظًا على الأمان. بعد إنشاء الحساب، نفّذ يدويًا في Supabase SQL Editor مع استبدال البريد:

```sql
update public.profiles
set role = 'admin', admin_role = 'super_admin', status = 'active'
where email = 'YOUR-ADMIN-EMAIL@example.com';
```

احتفظ بحساب مدير عام واحد على الأقل، وفعّل MFA من إعدادات Supabase قبل الإطلاق.

### إعداد البيئة
انسخ `.env.example` إلى `.env.local` وأدخل القيم الحقيقية. أهم المتغيرات:

```text
NEXT_PUBLIC_SITE_URL=https://your-domain.com
NEXT_PUBLIC_DEMO_MODE=false
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...
NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME=...
NEXT_PUBLIC_CLOUDINARY_API_KEY=...
CLOUDINARY_API_SECRET=...
OPENAI_API_KEY=...
NEXT_PUBLIC_DEFAULT_CURRENCY=ILS
```

**مهم:** لا تضع `SUPABASE_SERVICE_ROLE_KEY` أو `CLOUDINARY_API_SECRET` أو `OPENAI_API_KEY` في متغير يبدأ بـ `NEXT_PUBLIC_`.

### أوامر التشغيل

```bash
npm ci
npm run typecheck
npm run lint
npm run build
npm start
```

## ما يجب إنجازه قبل استقبال عملاء حقيقيين

### P0 — قبل الإطلاق مباشرة
1. تطبيق migration 2.0 واختبار الطلب من البداية للنهاية.
2. ربط بوابة دفع معتمدة للسوق أو تثبيت سياسة واضحة للدفع عند الاستلام.
3. ربط شركة شحن أو نظام مناطق وأسعار وتتبع للتوصيل.
4. إعداد بريد معاملات للترحيب وتأكيد الطلب وتغير حالته واستعادة الحساب.
5. مراجعة قانونية محلية للشروط والخصوصية وسياسة الاسترجاع والضرائب.
6. تفعيل MFA للإدارة، نسخ احتياطية، مراقبة أخطاء، وتنبيهات توفر الخدمة.
7. إجراء اختبار اختراق واختبار RLS بحسابات عميل وتاجر وإداري مختلف.
8. تشغيل build وlint وtypecheck في CI على كل تحديث.

### P1 — أول 90 يومًا
1. إضافة بوابات دفع وشحن متعددة بحسب السوق.
2. إضافة تقييمات موثقة بعد الطلب بدل أرقام تقييم يدوية.
3. إضافة تحليلات تحويل حقيقية: مشاهدة ← نقرة منتج ← سلة ← طلب ← إتمام.
4. تخزين rate limiting في Redis أو خدمة موزعة بدل ذاكرة كل خادم.
5. إضافة بحث متخصص مثل Typesense أو Algolia عند نمو الكتالوج.
6. إضافة نظام إشعارات بريدية وداخلية وPush.
7. إنشاء لوحة سياسات وإرجاع مستقلة لكل متجر ضمن حدود سياسة المنصة.
8. إضافة نظام نزاعات واسترداد وخدمة عملاء مع SLA.

### P2 — التوسع العالمي
1. نموذج بيانات للأسواق والعملات والضرائب واللغات بدل الإعداد العام الواحد.
2. تقسيم خريطة الموقع عند تجاوز عشرات آلاف الصفحات.
3. WAF وCDN وحماية bots ومكافحة احتيال ومدفوعات.
4. مستودع بيانات وتحليلات أحداث ومقاييس Cohort وRetention وLTV وCAC.
5. نظام توصية يتعلم من أحداث حقيقية مع اختبارات A/B وحوكمة للخصوصية.
6. فرق تشغيل ومراجعة محتوى ودعم محلي لكل سوق.
7. برنامج اكتساب تجار ومؤثرين، ومؤشرات جودة للمخزون والتوصيل.

## نتائج التحقق في بيئة المراجعة

- فحص ثابت لـ **117 ملف TypeScript/TSX**: لا أخطاء صياغة ولا استيرادات محلية مفقودة.
- توافق إصدار `package.json` و`package-lock.json`: **2.0.0**.
- فحص بنية معاملات وكتل SQL في المخطط وmigration الجديد.
- عدم العثور على مفاتيح API أو أسرار فعلية داخل الملفات.
- عدم وجود إدخال مباشر للطلبات من كود المتصفح بعد التعديل.

### قيد التحقق
لم يكتمل `npm ci` أو build الكامل داخل بيئة المراجعة لأن تنزيل الحزم لم يكتمل من مستودع npm المتاح، كما انتهت محاولة الاتصال المباشر بالمستودع العام بمهلة تنفيذ. لذلك يجب تشغيل أوامر التحقق الكاملة على جهازك أو CI متصل بـ npm قبل النشر. هذا ليس دليلًا على وجود خطأ في المشروع، لكنه يعني أن النسخة لم تحصل هنا على اختبار تشغيل نهائي عبر Next.js.
